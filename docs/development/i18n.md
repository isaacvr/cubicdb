# Internacionalización (i18n)

## Estado actual

El sistema actual es manual:
- Objetos TypeScript por idioma (`en-EN.ts`, `es-ES.ts`, `zh-ZH.ts`)
- Store reactivo (`globalLang`, `localLang`) que resuelve el objeto del idioma
- Acceso via `$localLang.section.key`
- Tipo `Language` define la estructura completa de todas las traducciones

### Problemas del enfoque actual

1. **No hay detección de keys faltantes en tiempo de compilación** entre idiomas.
2. **Archivos muy grandes**: todo el idioma es un objeto gigante.
3. **No soporta pluralización** ni interpolación compleja.
4. **No hay lazy loading**: se carga todo el idioma de una vez.
5. **Agregar un idioma** requiere copiar y traducir todo el objeto manualmente.

## Migración propuesta

Evaluar librerías que se integren bien con SvelteKit 5:

### Opciones

| Librería | Pros | Contras |
|---|---|---|
| **svelte-i18n** | Madura, stores reactivos, pluralización, lazy loading | Basada en stores (no runes) |
| **typesafe-i18n** | Type-safe completo, detección de keys faltantes en compilación, ligera | Más setup inicial |
| **Paraglide** (inlang) | Compilada, tree-shakeable, type-safe, soporte SvelteKit nativo | Relativamente nueva |

### Criterios de selección

1. Compatibilidad con Svelte 5 (idealmente runes)
2. Type-safety (detectar keys faltantes en compilación)
3. Lazy loading por idioma
4. Pluralización e interpolación
5. Developer experience (autocompletado de keys)

### Requisitos de migración

- Mantener los 3 idiomas existentes (EN, ES, ZH)
- No romper la UI existente durante la migración
- Las keys existentes (`$localLang.global.delete`) deben poder mapearse al nuevo sistema
- Migración incremental: se puede hacer sección por sección

## Regla general

Hasta que se migre, seguir usando `$localLang.section.key`.
Nunca hardcodear textos visibles al usuario en componentes.
